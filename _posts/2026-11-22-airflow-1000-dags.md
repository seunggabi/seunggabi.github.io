지금 맡고 있는 서비스 데이터 플랫폼의 Airflow 저장소에는 DAG 파일이 1,302개 있다. 운영 서버에서는 `.airflowignore`로 개발용 파일을 빼고 1,230개 남짓이 올라간다. 대부분은 MySQL에서 SQL 파일 몇 개를 순서대로 실행하는 집계 잡이다. Airflow 2.8.1, `LocalExecutor`, 스케줄러 한 대로 돈다.

DAG가 이만큼 많아지면 신경 쓸 곳이 셋이다. 파일을 다시 파싱하는 비용, 스케줄러 루프 한 번에 만들 수 있는 DAG run 수, 원천 DB에 동시에 붙는 쿼리 수다. 이 글은 그 세 곳에 맞춰 DAG를 만드는 방식과 설정을 정리한 것이다. 회사 내부 이름과 테이블 이름은 뺐다. 스케줄러가 파싱과 실행을 어떻게 나누는지는 [Airflow 스케줄러와 executor 글](/posts/airflow-scheduler-and-executors/)에 있다.

## DAG 파일은 이름만 다르고 내용은 같다

DAG 파일 하나는 팩토리 함수를 부르는 짧은 래퍼다. `dag_id`는 파일 이름에서 나오고, 대부분의 파일은 이름에 무엇을, 얼마나 자주 하는지가 들어 있다.

```python
# dags/mysql___d___stat___daily_order_count.py (이름은 예시)
import os
from batch.core.const import BATCH, STAT
from batch.core.airflow_dag_mysql import airflow_dag_mysql

DAG_ID = os.path.basename(__file__).replace(".pyc", "").replace(".py", "")
OWNER = "..."
START_DATE = "20250401"
DESCRIPTION = f"[{BATCH}] {DAG_ID}"
SCHEDULE_INTERVAL = "10 8 * * *"
DEFAULT_ARGS = {"owner": OWNER, "_start_date": START_DATE, "catchup": True}

dag = airflow_dag_mysql(DAG_ID, OWNER, START_DATE, DESCRIPTION,
                        SCHEDULE_INTERVAL, DEFAULT_ARGS, [BATCH, STAT])
```

| 이름 조각 | 뜻 | 예 |
|---|---|---|
| 팩토리 | DAG를 만드는 함수 종류 | `mysql`, `replay`, `request` |
| 주기 | 실행 간격 | `h`, `d`, `w`, `m` |
| 분류 | 결과 테이블 묶음 | `stat`, `extract` |
| 상세 | 잡 이름 | `daily_order_count` |

`catchup`과 `_start_date`는 `DEFAULT_ARGS`에 적지만, 팩토리가 꺼내서 DAG 인자로 넘긴다. 파일마다 바꿀 값을 한 딕셔너리에 모아 두려는 형식이다.

팩토리는 `dag_id`를 `___`로 잘라 SQL 폴더를 찾는다. `mysql___d___stat___daily_order_count`면 `mysql/d/stat/daily_order_count/` 아래 `*.sql`을 이름순으로 정렬하고, 날짜를 계산하는 `init` 태스크 뒤에 그 순서대로 태스크를 잇는다. SQL 파일 이름의 마지막 `___` 뒤가 그 쿼리를 보낼 MySQL connection id다. SQL 안의 `{date}`는 `init`이 계산한 날짜로, `{value}`는 바로 앞 태스크가 XCom으로 넘긴 행으로 바뀐다. 앞 태스크 결과가 0행이면 그 단계는 `SELECT 1`로 건너뛴다. XCom은 메타데이터 DB에 저장되므로 이 방식은 행 수가 적은 집계 결과를 넘길 때만 쓴다.

```text
mysql/d/stat/daily_order_count/
  d___1___source_db.sql      # 원천 DB에서 집계
  d___2___dashboard_db.sql   # {value}로 받은 행을 대시보드 DB에 저장
```

집계 하나를 추가하려면 폴더를 만들어 SQL 파일을 번호 순서로 넣고 DAG 파일 하나를 복사하면 된다. SQL 파일이 든 폴더가 750개 가까이, SQL 파일이 5,800여 개다. MySQL 팩토리를 쓰는 DAG가 751개로 가장 많고, 다른 DAG의 지난 N일을 다시 돌리는 replay 팩토리가 375개다.

## 파일 하나에 DAG 하나

DAG 1,000개를 한 파일에서 반복문으로 만들 수도 있다. 그러지 않은 이유는 파싱이 파일 단위로 일어나서다. 스케줄러의 DAG 파일 처리기는 파일마다 프로세스를 하나씩 띄워 `parsing_processes`만큼 동시에 파싱한다. 파일 하나가 DAG 1,000개를 만들면 그 파일 하나가 병렬화되지 않는 덩어리가 되고, 타임아웃에 걸리면 DAG 1,000개가 한꺼번에 import error로 사라진다. 파일이 하나씩이면 파싱에 실패해도 그 DAG 하나만 빠지고, 느린 파일 하나가 다른 DAG의 파싱을 붙잡지 않는다.

대가는 파일 개수다. 그래서 파싱 시점 코드를 가볍게 두는 규칙을 둔다. DAG 파일과 팩토리는 import 시점에 원천 DB나 외부 API를 부르지 않는다. Kafka 클라이언트처럼 무거운 라이브러리는 태스크 함수 안에서 import한다. EMR에서 도는 SQL 잡은 SQL 본문을 실행 시점에 S3에서 읽는다.

규칙에서 벗어나는 곳이 셋 있다. 공통 모듈은 import될 때 Slack 알림 설정을 Airflow Variable에서 한 번 읽는다. 팩토리는 데이터 계보(lineage)를 남기려고 파싱할 때 SQL 파일을 SQL 파서로 읽는다. 그리고 메타데이터 DB에 그 connection 이름의 pool이 있는지 묻고, 없으면 만든다. 셋 다 메타 DB나 CPU를 쓰는 일이라, 파일 수가 늘면 파싱 한 바퀴가 길어지는 원인이 된다. pool은 아래 절에서 다시 다룬다.

환경별로 올라가지 않아야 하는 DAG는 `.airflowignore`로 거른다. 개발 서버에는 `_prd`가 붙은 파일을, 운영 서버에는 `_dev`가 붙은 파일을 빼는 정규식 파일을 따로 두고, 재시작 스크립트가 환경에 맞는 쪽을 `dags/.airflowignore`로 링크한다.

## 설정은 파싱, 스케줄링, 실행 순서로 잡았다

설정 파일은 `base.cfg` 하나에 환경별로 바뀌는 키만 `prd.cfg`, `dev.cfg`에 둔다. 배포 스크립트가 base에 환경 파일의 키를 덮어써 `airflow.cfg`를 만든다. base에 없는 키가 환경 파일에 있으면 생성을 실패시킨다. Airflow는 모르는 키를 조용히 무시하므로, 오타 난 키가 운영에서 아무 효과 없이 남는 일을 이 검사로 막는다.

| 키 | Airflow 2.8.1 기본값 | 운영 값 |
|---|---|---|
| `[scheduler] min_file_process_interval` | 30 | 300 |
| `[scheduler] dag_dir_list_interval` | 300 | 120 |
| `[scheduler] max_dagruns_to_create_per_loop` | 10 | 160 |
| `[scheduler] max_dagruns_per_loop_to_schedule` | 20 | 320 |
| `[core] parallelism` | 32 | 36 |

파싱부터 보면, `min_file_process_interval` 300은 같은 파일을 적어도 5분이 지나야 다시 파싱한다는 뜻이다. 한 바퀴가 5분보다 길면 간격도 그만큼 길어진다. 배포 전 검사처럼 한 프로세스에서 DagBag 전체를 읽으면 10초 안팎이지만, 스케줄러의 파일 처리기는 파일마다 프로세스를 띄우고 위의 Variable 조회와 pool 확인을 파일마다 한다. 파일 1,300개를 파싱 프로세스 4개가 나눠 읽으니, 한 바퀴가 30초를 넘으면 기본값에서는 처리기가 쉬지 않고 돈다. 새 DAG 파일은 `dag_dir_list_interval` 120초 안에 발견된다.

스케줄링 쪽 두 키는 역할이 다르다. `max_dagruns_to_create_per_loop`은 루프 한 번에 새로 만들 DAG run 수이고, `max_dagruns_per_loop_to_schedule`은 루프 한 번에 태스크를 배정할지 살펴볼 run 수다. 일 배치 260여 개는 대부분 아침 6~8시에 시작하고, replay 375개는 새벽 0~5시에 나뉘어 돈다. 월요일 새벽 1~2시에는 주 배치 230여 개가, 매월 1일 0~1시에는 월 배치 280여 개가 더해진다. 두 값을 크게 두면 같은 시각에 몰린 run을 루프 몇 번에 나눠 만들지 않는다.

실행 쪽 `parallelism` 36은 스케줄러 한 대가 동시에 돌리는 태스크 수의 상한이다. 스케줄러가 한 대라 지금은 서버 전체의 상한과 같다. `LocalExecutor`에서는 이 수만큼 태스크 프로세스가 같은 서버에 뜨고, 태스크 프로세스도 메타데이터 DB에 연결한다. `max_active_runs_per_dag`과 `max_active_tasks_per_dag`은 10이다. run 수는 공통 DAG 클래스가 `max_active_runs=1`을 넣으므로 DAG마다 1이고, 태스크 수 상한 10은 그대로 적용된다.

## 동시 실행은 pool로 원천 DB마다 막는다

`parallelism`은 스케줄러의 상한이고, 원천 DB를 보호하는 것은 pool이다. 팩토리는 SQL 파일 이름에서 얻은 connection id를 그대로 그 태스크의 pool 이름으로 쓴다. 크기는 connection별로 코드에 정해 둔다. 운영 읽기 DB 36, 쓰기 DB 16, 대시보드 DB 20, 개발 DB 4, 외부 메일 발송 1이고, 목록에 없는 connection은 12다. 운영 읽기 DB pool은 `parallelism`과 같은 36이라, 읽기 쿼리는 사실상 스케줄러 상한까지 쓸 수 있다.

connection과 pool을 같은 이름으로 묶으니 새 원천을 붙일 때 pool을 따로 만들 일이 없다. 대신 pool 확인과 생성이 파싱 경로에 들어간다. 이미 있으면 아무것도 하지 않고, 실패하면 예외를 삼켜 DAG 파싱은 계속된다. 그때 pool이 끝내 없으면 그 pool을 쓰는 태스크는 실행되지 못하므로, pool 목록은 화면에서 따로 확인한다. 생성만 하는 함수라 이미 있는 pool의 크기를 바꿀 때도 화면이나 CLI에서 직접 바꾼다. 슬롯이 여러 층에서 막히는 순서는 [스케줄러 글](/posts/airflow-scheduler-and-executors/)에 정리했다.

## 날짜 순서를 지키는 기본 인자와 멈춘 run 정리

```python
DEFAULT_ARGS = {
    "depends_on_past": True,
    "retries": 2,
    "retry_delay": timedelta(minutes=1),
    "retry_exponential_backoff": True,
    "max_retry_delay": timedelta(minutes=10),
}
# 공통 DAG 클래스가 max_active_runs=1, catchup=False(DAG 파일에서 True로 덮어씀), Slack 실패 알림을 붙인다
```

집계 잡은 어제 결과 위에 오늘을 쌓는 것이 많아 `depends_on_past=True`, `max_active_runs=1`로 날짜 순서를 지킨다. DAG 파일 중 741개는 `catchup=True`로 덮어써서, 서버가 멈췄다 돌아오면 빠진 날짜부터 순서대로 다시 돈다. 같은 날짜를 다시 돌려도 결과가 같아야 하는 이유는 [멱등 DAG 글](/posts/airflow-idempotent-dags/)에 있다.

DAG 수백 개가 catchup으로 지난 날짜를 돌면 그 태스크들이 슬롯을 차지해서, 오늘 돌아야 할 시간 단위 잡이 슬롯을 못 얻는다. 그래서 시간 단위 잡, 분 단위 cron 잡, EMR 잡에 `priority_weight=100`을 줘서 밀린 태스크보다 먼저 슬롯을 잡게 했다.

순서를 지키는 대신 한 run이 꼬이면 뒤가 다 멈춘다. 태스크는 다 끝났는데 DAG run이 `running`으로 남거나, 태스크가 `scheduled`·`queued`에서 오래 머무는 경우다. 매시간 도는 정비 DAG가 둘을 따로 정리한다. `running`으로 남은 run은 기간 제한 없이 보고, 태스크가 전부 `success`이고 마지막 태스크가 끝난 지 30분이 지난 경우에만 성공으로 닫는다. 건너뛰거나 실패한 태스크가 있는 run은 닫지 않는다. 멈춘 태스크는 최근 2일 run에서 30분 넘게 머문 것을 찾아 한 번에 최대 200개까지 clear하고, pool 슬롯이 없어 기다리는 태스크는 건드리지 않는다.

사람이 직접 고칠 때는 Airflow 화면에 버튼을 붙이는 크롬 확장을 쓴다. DAG 하나, 또는 끝나지 않은 run이 있는 MySQL DAG 전체를 날짜 순서대로 다시 돌게 clear한다. 실행 전에 대상만 보여 주는 dry-run이 있다.

## 배포 전에 DagBag 전체를 읽는다

DAG 1,200개에서는 import error 하나를 화면에서 찾기 어렵다. 배포 스크립트는 새 코드를 운영 경로로 옮기기 전에 빈 sqlite 메타 DB를 대상으로 DagBag 전체를 읽고, import error가 0개이고 DAG 수가 파일 수 이상인지 확인한다. 실패하면 배포를 멈춘다. 다만 `requirements.txt`가 바뀐 배포는 기존 가상환경으로 검사할 수 없어 이 단계를 자동으로 건너뛴다. 의존성이 바뀌는 배포가 가장 위험한데 그때 검사가 빠지는 셈이다.

스케줄러는 한 대를 전제로 설정했다. 재시작 스크립트는 다른 계정으로 뜬 스케줄러가 있으면 재시작을 중단하고 끝난다. systemd 밖에서 같은 계정으로 남아 있는 scheduler·webserver 프로세스는 정리한 뒤 다시 띄운다.

## 묻고 답하기

Q. 스케줄러를 늘리면 되지 않나?

Airflow 2는 메타 DB가 `SKIP LOCKED`나 `NOWAIT`를 지원하면(MySQL 8.0 이상, PostgreSQL 12 이상) 스케줄러를 여러 대 띄울 수 있다. `LocalExecutor`에서는 스케줄러마다 자기 서버에서 태스크를 돌리고 `parallelism`도 스케줄러마다 적용되므로, 늘리면 태스크를 도는 서버와 동시 실행 상한이 함께 는다. pool은 메타 DB에 있으니 원천 DB 보호는 그대로다. 파싱만 떼어 내는 방법도 있다. 2.3부터 `standalone_dag_processor`로 파일 처리기를 별도 프로세스로 띄울 수 있고, Airflow 3에서는 DAG processor를 따로 띄워야 한다. 지금은 스케줄러 한 대 안에서 파싱까지 한다.

Q. SQL만 바꿨는데 화면의 쿼리는 예전 것이다. 어느 쪽이 실행되나?

새 SQL이 실행된다. 팩토리는 파싱할 때 SQL 파일을 읽어 태스크에 넣는데, 태스크를 실행하는 `airflow tasks run` 프로세스가 시작할 때 DAG 파일을 다시 import하므로 그때 파일에 있는 SQL을 읽는다. 이미 실행된 태스크의 Rendered Template 화면은 실행 때 저장된 값이라 새 SQL이 보인다. 아직 돌지 않은 태스크나 태스크 상세 화면은 스케줄러가 저장한 직렬화본을 보여 주므로, 파일이 다시 파싱될 때까지 예전 SQL이 보일 수 있다. 배포 때는 스케줄러를 재시작하므로 전체가 곧 다시 파싱된다.

## English summary

Our Airflow 2.8 install runs about 1,230 DAGs from 1,302 DAG files on one scheduler with LocalExecutor, mostly MySQL aggregation jobs. Each DAG file is a short wrapper around a factory; the file name encodes factory, frequency, group and job, and the factory turns the sorted SQL files in the matching folder into a task chain. One DAG per file keeps parsing parallel and limits an import error to one DAG. The config is a base file plus per-environment overrides, with a check that rejects unknown keys. Each file is re-parsed at most every five minutes, the scheduler creates many more DAG runs per loop for the early-morning and month-start peaks, and a pool named after each connection protects each source database. A full DagBag load runs before deploys, because one broken file is hard to spot among a thousand.
